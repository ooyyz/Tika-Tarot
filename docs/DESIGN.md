# Tika Tarot 首版设计文档

版本：0.3 首版实施基线

日期：2026 年 9 月 30 日

用途：作为界面、牌面、功能和验收的共同依据。首版核心功能已实现，实测范围与未覆盖项见 `outputs/ACCEPTANCE.md`，不将计划验收项视为全部通过。

## 1 产品目标与约束

做一个有纸牌触感、能专注完成一次抽牌并留下记录的本地网页工具。核心体验是「提出问题 → 洗牌 → 选牌 → 翻牌 → 阅读 → 留下记录」。

用户已确定的要求：

- 在本地网页运行，不需要服务器。
- 首版只做 22 张大阿尔卡那，使用统一的几何图形、星象符号和纸张纹理。
- 打磨抽牌、翻牌、牌阵和保存记录。
- 本地仓库位于桌面 `Tika-Tarot` 文件夹，关联 `git@github.com:ooyyz/Tika-Tarot.git`。
- 后续所有项目成果保存在该文件夹内，由用户在阶段完成后指令提交版本。

用户已确定的视觉基色：桌布深蓝 `#1A3A5F`、浅蓝 `#8EC4E9`、霜色 `#E8F4F8`，搭配金色。本文在此基础上提出霜色纸牌、具体金色和辅助色；中文界面、单张与三张牌阵、可选逆位、手动选牌、自动保存已完成记录仍作为可调整的默认方案。

运行标准：用户解压或复制完整项目后，双击 `index.html` 即可使用。运行时不需要 Node.js、终端、网络、API Key、账号或本地 HTTP 服务。首要验收环境是 macOS 上的 Chrome 与 Safari；验收时记录实际版本。布局兼容窄屏，但不把移动系统本地文件打开能力作为首版承诺。

## 2 首版范围

| 包含 | 明确行为 |

| 22 张牌 | 编号 0 至 21，中文牌名、英文辅助名、正逆位含义、反思问题、独立牌面图形 |

## 3 页面与操作路径

采用单页应用外观，顶部三个入口：「抽牌」「牌册」「记录」。切换入口不刷新文档，不依赖服务端路由。设置使用轻量弹层。

### 3.1 抽牌桌面

桌面宽屏布局：顶部品牌与导航；中间主牌桌；右侧约 320px 阅读栏；底部随阶段变化的主操作。初始阶段右侧放牌阵说明，翻牌后放当前选中牌的解读。

- 初始：问题输入框、两种牌阵选择、逆位开关、「洗牌并开始」。三张牌阵为默认。
- 选牌：牌位显示名称和序号；牌池全部显示背面；状态为「已选 0 / 3」。已选牌进入最左侧空牌位。
- 翻牌：选满后收起未选牌，突出牌阵与「点击翻牌」「全部翻开」。
- 完成：展示记录保存状态、笔记区、「再抽一次」。点击任意正面牌切换解读。

窄屏小于 768px：开始前将问题、牌阵和开始按钮放在牌位之前；开始后阅读栏移至牌阵下方；三张结果并排紧凑显示，点击后在下方阅读大图和释义。选牌池采用可纵向滚动的网格，不用横向长扇形。320px 宽度下不产生页面横向滚动。

### 3.2 牌册

展示 22 张缩略牌、编号和中文名称，点击打开详情。详情允许切换正逆位释义，但不改变当前牌局或全局逆位开关。使用同一牌面组件，避免为牌册制作第二套图像。

### 3.3 记录

按创建时间倒序排列。摘要包含时间、问题、牌阵、抽到的牌名与正逆位。点击进入只读牌阵回放，可编辑笔记；回放不生成新记录、不重新随机、不覆盖当前抽牌进度。

首版不加搜索和标签。空态显示「还没有记录，完成一次抽牌后会出现在这里」。删除单条前显示具体问题与时间并确认，不提供一键清空全部。

## 4 抽牌规则与状态

### 4.1 状态流转

`准备 → 洗牌中 → 选牌中 → 待翻牌 → 部分翻开 → 全部翻开`

单张牌从「待翻牌」直接进入「全部翻开」。保存状态是独立状态：`未完成／保存中／已保存／仅本次会话／保存失败`，不能因保存失败阻止阅读或导出。

| 状态 | 可操作 | 约束 |
| --- | --- | --- |
| 准备 | 修改问题、牌阵、逆位与开始 | 生成本局 ID，拍下设置快照后才开始洗牌 |
| 洗牌中 | 减少动态时直接完成 | 屏蔽重复开始，不生成第二局 |
| 选牌中 | 点击未选背面牌、重新开始 | 已选牌不可重复选择或撤回，不展示身份 |
| 待翻牌 | 任意位置翻牌、全部翻开 | 不能补牌或更换已选牌 |
| 部分翻开 | 继续翻牌、查看已翻牌释义 | 点击已翻牌只选择阅读对象，不翻回背面 |
| 全部翻开 | 阅读、笔记、导出、再抽一次 | 按本局 ID 保存一次；后续笔记只更新原记录 |

开始后冻结问题、牌阵和逆位；重新开始才允许修改。已有选牌而未完成时，重新开始须提示「本次尚未完成，重新开始会放弃已选牌」。打开牌册、记录、设置再返回时保留内存中的当前牌局。

首版不做未完成牌局的刷新恢复。刷新或关闭会丢弃未完成牌局；已产生未保存数据时可使用浏览器允许的离开提示，但不依赖它保证数据。界面在选牌区以小字说明「完成翻牌后保存」。

### 4.2 随机与公平性

- 对 22 个唯一 ID 采用 Fisher–Yates 洗牌；禁止使用 `sort(() => Math.random() - 0.5)`。
- 默认使用 `crypto.getRandomValues`；整数采样使用拒绝采样避免取模偏差。若环境无法提供随机源，明确提示并停止开始，不悄悄使用固定序列。
- 一局开始时固定每个牌池位置的牌 ID 和正逆位。点击只选择位置，不重新随机。
- 逆位关闭时全部为正位；开启时以独立随机位生成朝向，牌背保持完全相同。
- 一局内不能出现重复牌；不同局可以重复。洗牌动画长度、点牌顺序以外的操作和问题文本不影响概率。
- 牌位按用户选中顺序分配，三张依次对应「现状」「阻碍」「建议」。
- 背面状态的 DOM 可访问名称只包含「第 N 张待选牌」，不通过标题、颜色、尺寸或读屏文本透露身份。这是体验约束，不承诺对开发者工具隐藏本地数据。

### 4.3 保存与笔记

最后一张牌翻开并进入逻辑完成状态后触发保存，不依赖 CSS 动画结束事件。失败时保留内存数据并允许导出，重试沿用同一 ID，防止双击和重复事件造成重复记录。

笔记最多 2,000 个字符，输入后约 500ms 防抖保存；离开笔记区或切换页面时立即刷新写入。状态文案区分「已保存」「笔记未保存」与「仅本次会话」。问题及已经抽出的结果不能在历史中修改，避免回顾时混淆。

## 5 视觉与牌面系统

### 5.1 蓝金霜色主题

风格为冷色纸上星图：深蓝桌布承托霜色纸牌，浅蓝用于星光与交互，柔和金色用于边框和仪式感细节。纸牌保留细小纤维与哑光质感，霜色表达冷白纸张，不使用透明玻璃或冰晶材质效果。桌布采用低对比织物纹理，不堆叠霓虹发光或大面积粒子动画。

下表中三种基色由用户指定；其余为扩展建议。颜色按角色复用，不能为每张牌另起一套主题。

配色分工：

- 桌布主体保持指定的 `#1A3A5F`，暗部仅少量使用午夜蓝；阅读栏用面板蓝形成层次。深蓝覆盖大部分背景，浅蓝负责操作识别，金色只集中在细线、星点和关键动作。
- 牌面以霜色为底、深蓝为主线，浅蓝只画辅助轨道和装饰。香槟金适合装饰描边；需要清楚辨认的浅底符号与小字改用古金。
- 「洗牌并开始」用香槟金底配深蓝字，悬停改浅金；「全部翻开」等普通主操作用浅蓝底配深蓝字，悬停改冰蓝。次级按钮用面板蓝底配霜色字，悬停改悬停蓝。
- 已选牌显示浅蓝边框与序号标记；键盘焦点在深底使用浅金外环，在霜色底使用深蓝外环，不能仅依赖发光或颜色差异。
- 逆位不染红整张牌；深底标签使用灰紫蓝，霜色底的「逆位」文字仍用深蓝。成功与失败色仅用于深底反馈，浅底反馈使用深蓝正文加状态图标；不把状态色扩散到整套牌面。
- 禁用态用午夜蓝底、银蓝文字，并移除悬停和点击反馈；避免直接降低整个控件的透明度造成文字过淡。

实色配对的对比度计算：霜色／桌布深蓝约 10.32:1，银蓝／面板蓝约 4.98:1，浅蓝／面板蓝约 4.83:1，深蓝／浅蓝按钮约 6.19:1，深蓝／香槟金按钮约 5.04:1，雾蓝灰／霜色约 5.30:1，古金／霜色约 5.17:1。香槟金在面板蓝上仅约 3.93:1，因此深底金色小字统一使用浅金。正文配对以至少 4.5:1 为验收目标，实际叠加纹理、透明度和状态样式后还需复查。

中文标题优先系统宋体（如 Songti SC），正文使用系统无衬线（如 PingFang SC），英文与编号用 Georgia。所有字体都有系统回退，不加载在线字体。正文 16px，辅助文字不低于 12px；操作热区至少 44 × 44px。

### 5.2 牌面构成

- 统一比例 2:3，SVG 坐标系 `0 0 240 360`；主牌宽度建议 176–208px，牌册缩略图可缩放。
- 四角轻圆角；两道细边框；顶部编号；中央几何图腾；底部中文名与较小英文名。
- 每张中央主图限定 1 个核心母题、最多 3 种基本几何元素；共享星点、轨道、月相、放射线装饰语汇。
- 星象图形作为装饰，不附会成一套未经确定的占星对应关系。用 SVG 路径绘制，不依赖不同系统的 Unicode 符号字体。
- 纸纹由低透明度、固定种子的 SVG 噪声或本地纹理资产生成；牌名区纹理更弱。禁止每帧重生成纹理。
- 牌背为午夜蓝 `#10263F` 底、香槟金 `#C9A66B` 双框、浅蓝 `#8EC4E9` 中心双环星图，采用 180° 旋转对称，避免泄露正逆位。
- 逆位时中央图案旋转 180°，标题和编号保持可读；牌下明确标注「正位／逆位」。这是数字阅读的设计选择。
- 翻转使用外层容器，逆位旋转使用内层图案，两种变换不能覆盖彼此。

每张牌已补齐：正位与逆位各 2–4 个关键词、各 60–100 字原创解释、各一条反思问题。解读面板分别展示牌位提示与该朝向牌义，不伪装成理解了用户自由输入问题的 AI。逆位不等于坏事；「死神」的文案围绕结束与转化，不能解读成现实死亡断言。

### 5.4 动效与可访问性

| 交互 | 默认表现 | 减少动态模式 |
| --- | --- | --- |
| 洗牌 | 约 700ms，少量叠牌交错 | 立即切换状态 |
| 悬停／聚焦 | 上移约 4px，加焦点边框 | 仅边框 |
| 选牌入阵 | 约 280ms，移向空牌位 | 立即入阵 |
| 翻牌 | 约 480ms，Y 轴翻转 | 直接显示正面 |
| 全部翻开 | 间隔约 120ms 开始翻转 | 同时显示 |

系统 `prefers-reduced-motion` 与应用设置任一要求减少动态时即启用。没有持续自动运动。键盘 Tab 可遍历牌按钮，Enter／Space 选牌或翻牌，Esc 关闭详情弹层并返回触发位置；弹层管理焦点。保存状态和翻牌结果使用温和的读屏通知，不逐帧播报。

## 6 本地技术方案

### 6.1 零服务器入口

采用 HTML、CSS、原生 JavaScript 和本地 SVG。脚本用经典 `<script defer src="...">` 按依赖顺序加载，通过一个 `window.TikaTarot` 命名空间组织职责，避免散落全局变量。

不在运行入口使用 ES Modules、动态 import、fetch 本地 JSON、CDN、远程字体、远程图片或 Service Worker。牌数据写在经典 JS 数据文件中；所有运行资源用相对路径引用。ES Modules 通过 `file://` 打开会遇到 CORS 限制，不能以要求用户启动服务器来规避本项目约束。[MDN 模块运行说明](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules#other_differences_between_modules_and_classic_scripts)

后续可以添加开发侧校验脚本，但生成的应用仍须直接打开；首版不引入打包器和 UI 框架。SVG 主图来自项目维护的固定模板，用户输入只作为文本渲染。

当前目录如下；随机与牌阵逻辑合并在 `core.js`，样式集中在 `app.css`：

### 6.2 存储与备份

`localStorage` 作为便利性自动保存，JSON 文件作为可迁移备份。对 `file://` 文档，浏览器并未统一保证 localStorage 行为，迁移文件路径、切换浏览器或清理浏览数据后不能假定历史仍在。[MDN 本地文件存储限制](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage#description)

- 启动时在 try/catch 内获取存储对象并执行写入、读取、删除探测，不能只检查属性存在。
- 存储成功：提示「已保存在此浏览器」，记录页保留「导出备份」入口。
- 不可用：进入内存模式，提示「当前无法长期保存，关闭前请导出记录」；抽牌、笔记、查看和导出仍可用。
- 写入失败：显示失败状态与导出入口，不删除旧数据，不显示「已保存」。
- 存储内容损坏：保留原始值，允许下载原始数据并进入内存模式；不得初始化空数组覆盖损坏内容。未知新版 schema 同样处理。
- 不保证多窗口同时写入的一致性；首版按单窗口使用设计，读取到外部更新时提示重新加载记录，避免无提示覆盖。
- 只保存文本与卡片 ID，不存 SVG、截图或完整牌库。重新打开记录仍使用其保存的释义快照，后续文案改版不改变旧记录含义。

备份使用 `Blob` 加下载链接导出，文件名 `tika-tarot-backup-YYYYMMDD-HHmmss.json`；通过文件选择器读入。浏览器不承诺自动写入项目目录，可让用户在保存对话框选择 `outputs/private/`，或依其浏览器下载设置保存。不能把「保存记录」描述成已自动创建项目内文件。

导出默认包含全部已完成记录、笔记与基础设置，不包含未翻开的牌局。导入前展示记录条数和冲突情况；校验通过且用户点击「导入」后合并，不覆盖现有记录。相同 ID 且内容相同跳过；相同 ID 但内容不同则作为新 ID 导入，并报告数量。未知版本、非法卡片、同局重复卡片、错误牌位或非布尔朝向均拒绝导入，保留现有数据。

单次导入限制 5MB、1,000 条；问题 200 字、笔记 2,000 字、释义单字段 500 字，白名单挑取字段，所有字符串按文本显示。首版不设自动删除旧记录的数量上限；容量不足时明确失败并提供导出。

### 6.3 数据模型


存储键使用 `tika-tarot:v1`。所有读取入口都校验结构；更新采用新对象序列化后一次写入，保留失败前的已知有效状态。随机、存储、UI 分离，以便逻辑测试无需启动浏览器页面。

## 7 阶段与验收

完成阶段不等于获准提交；每次 commit 或 push 等待用户明确指令。以下阶段是建议顺序，不自动开始下一阶段。

| 阶段 | 交付 | 达标依据 |
| --- | --- | --- |
| M0 设计基线 | 桌面仓库、远程关联、本文与协作约定 | 已完成：目录可访问、origin 正确、设计涵盖首版闭环 |
| M1 视觉原型 | 可本地打开的静态界面、统一牌背、愚者／月亮／世界三张样牌 | 宽屏与窄屏均可读；确认色彩、纹理、线条与翻牌风格 |

| M3 本地记录 | 自动保存、笔记、回放、删除、导入导出与存储失败降级 | 关闭重开在受测环境恢复；备份能还原；失败不假报成功 |
| M4 首版验收 | 动效和键盘打磨、离线验证、运行说明与交付包 | 以下验收清单通过，记录浏览器版本和已知限制 |

- [ ] 完整目录双击 `index.html` 打开，无依赖安装；断网后抽牌、翻牌、牌册、记录和导出可用，无外部网络请求。
